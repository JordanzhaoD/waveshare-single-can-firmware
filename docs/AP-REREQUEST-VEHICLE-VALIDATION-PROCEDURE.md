# 8.3.6防甩机制（AP 取消重请求协调器）单 CAN 实车验证规程（两级，2026-09-13，适配 waveshare-single-can-firmware v1.18）

> 本规程由双 CAN 规程（LILYGO-T-2Can 4.5.0-beta09 版，2026-09-12）改写。
> 协调器语义完整移植（2400ms 窗口 + 车辆侧自动重武装 + 延时链删除 +
> P1 拒激活提示 + P2 flag 直方图），但 **own-echo / counter 跟随行为与
> 接线强相关：双 CAN 的 9 轮 Tier 1 实车数据一律不继承，单 CAN 从零
> 重新验证**。双 CAN 侧数据此后仅作形态参考。

## 决定与前提

**AP 注入门控是 8.3.6防甩机制的运行前提**（沿用 2026-09-11 定义的整体框架）：

- **门控关 = 机制完全静默**：不触发轮次、不发送 0x045、不拦截任何注入——
  Legacy 走原始直通路径，这是**非 8.3.6 车型的正常设计模式**；
- 门控关时「8.3.6防甩机制」开关**仍可拨动**（记住你的选择，状态行显示
  「不可用 · AP 门控未开启」），门控重新打开后**自动恢复武装**，无需重拨开关；
- 门控开 + 开关开 = 协调器成为唯一激活权威（本规程要验证的模式）。

v1.18 是**合并单版本**：观察层（P1 车辆拒激活提示 / P2 flag 直方图）与完整
协调器同版落地，**8.3.6 开关默认关闭**。同版删除了旧 steer defense 全家
（Instant Engage / Minimal Inject / Soft Engage / 延迟注入，无并存开关），
**Abort Guard 保留**（它是 0x399 状态 8/9 锁存安全闸，协调器注入路径
从它经过——与本验证相互独立，保持默认关即可；开启后 8/9 级联期间会按
设计阻断激活注入，判读时注意区分）。

### 与双 CAN 的关键差异（上车前先知道）

| 差异点 | 双 CAN（beta09） | 单 CAN（v1.18，本规程） |
|---|---|---|
| 总线 | 双路独立 CAN，0x045 在其一 | **单路 TWAI**——0x045 是否可见取决于接线，必须现场复核（Tier 0 第 1 步） |
| own-echo | 已 9 轮实车验证 | **首验**：单总线上自己发的 0x045 会回到自身 RX，回声识别/counter 锚定行为必须重看（Tier 1 重点观察项） |
| counter 跟随 | 已验证 | **首验**（接线相关，同上） |
| AP 门控开关位置 | FSD 防护页内 | **驾驶舱页「AP 注入安全」卡**（`AP 门控` 开关；防护页只有 8.3.6 卡） |
| 诊断挂载 | `/status` → `legacyInjectionSafety.apReRequest` | **`/status` 顶层 `apReRequest` 对象**（`/defense_config` 另有 flat `ap_re_request` 开关态） |
| 防护页卡片顺序 | 总开关 → 门控两卡 → 8.3.6 | 总开关 → **Abort Guard 卡** → **8.3.6 卡** → 保护参数 |
| 烧录产物 | `_ota_app.bin` | **`firmware.bin`**（release 应用镜像；`merged-flash.bin` 是 esptool 整镜像，OTA 别传） |

## 触发机制速览（先懂这个再上车）

| 事实 | 含义 |
|---|---|
| 一轮只在 **AP 激活边沿**触发（武装中 + intent 在 + 见过完整退出） | 开着开关正常激活 AP（拨杆或车机均可）就触发，无需额外操作 |
| **握手术中碰物理拨杆 → 本轮锁死**（reason=`physicalInput`） | 一轮约 2-3 秒，期间手扶方向盘但**别碰拨杆** |
| **车辆侧异常（窗口过期/AP 退出/AP 自恢复/故障态）→ 自动重武装**，连续 3 次后才真锁死（`autoRearmLimit`） | 大多数异常**无需任何开关操作**，正常重新激活 AP 即开下一轮 |
| 硬件类锁死（计数器冲突/发送失败等）→ **开关关→开** 重新武装 | 排查/复测的标准动作 |
| 一轮的体感：AP 激活 → 自己取消（约 0.2-0.5s）→ **静默等车回可用态（约 1-1.5s，此间 AP 保持关闭）**→ 自己重新请求恢复（约 0.2-0.5s）| **这是设计行为，不是车辆故障**；不恢复=AP 保持关闭（安全态） |
| 测完开关关 = 完全回到旧行为 | 随时可用开关终止实验 |

## Tier 0：停车检查（P 挡、通电、设备在车）

前置（刷机）：WebUI OTA 上传 `firmware.bin`；重启后侧栏/系统状态版本 =
**1.18**；FSD 防护页从上到下依次为「FSD 防护总开关」→「Abort Guard」→
「**8.3.6 防甩协调器**」卡（徽标「实验 · 未验证实车防甩」，描述含
"需先开启「AP 注入门控」（驾驶舱 AP 注入安全页）"）。

1. **0x045 可见性复核（单 CAN 新增前置，最重要的一步）**：开录制器 120
   秒，过滤 `45,399,3EE`（hex，逗号分隔）。预期 CSV：
   - **0x045 R 帧流 ~10Hz**（拨杆心跳。单路接线若看不到 0x045，协调器的
     native 模板与拨杆检测器全部失效——**直接 No-Go**，先解决接线）；
   - 0x399 R ~2Hz、0x3EE R（mux0/mux1 各 ~1Hz）；
   - 顺手确认 **0x488**（转向扭矩）是否可见：可见则 Tier 1 把它加进过滤
     列表（掉线瞬间有无物理转向动作的直接证据）；不可见则 Tier 1 的
     掉线鉴别退化为体感 + 0x399 时序（见方案 A 的降级说明）。
2. **录制器不关**。去驾驶舱页「AP 注入安全」卡**确认「AP 门控」已打开**，
   回防护页打开「8.3.6防甩机制」开关，立即看诊断（`/status` 顶层
   `apReRequest` 对象，或防护页卡片诊断格）：
   - `requested=true`、`profileReady=true`、`apGateOpen=true`（**不得再有**
     `sourceUnconfigured`/`apGateOff` 之类的 unavailableReason）、`permit=true`；
   - `phase=WaitDriverIntent`，`reason=waitIntent` 或 `waitApActive`
     （停车两者皆正常，取决于 intent 选择是否在）。
3. **拨真实拨杆**：前推一次、后拨一次（停车，车不会有反应）。
   预期：诊断 `physicalInputRx` **+2**，phase **不变**（非握手术中不锁）。
   ——这一步在真车上直接验证了标定 byte0/0x03 在单 CAN 接线下读的是
   对的字段；**若 +0，说明 0x045 实际不可见，回到第 1 步查接线**。
4. **门控 关→开 验证（录制不关）**：去驾驶舱页关掉「AP 门控」→ 诊断变
   `effective=false`、`apGateOpen=false`、`phase=disabled`，状态行显示
   **「不可用 · AP 门控未开启」**（8.3.6 开关本身仍可拨，仅记忆状态）。
   此状态下再拨杆前推/后拨各一次：`physicalInputRx` 照常 **+2**（检测器
   仍在被动读总线），但 phase 保持 disabled、round=0、不锁死。重新打开
   门控 → 诊断恢复 `effective=true`、`phase=waitDriverIntent`
   （**自动重新武装，无需重拨 8.3.6 开关**）。
5. **停止录制，下载 CSV**：全程**零 0x045 T 行**（停车不发，含第 4 步
   门控关闭窗口）。协调器按设计只在 AP 激活边沿才开轮，停车时 AP 不会
   激活——**TX 组帧/counter/CRC 链路只能 Tier 1 验**，Tier 0 能查的是
   其余一切。

**Tier 0 全过 → Tier 1。任何一步不符 → 停，把 CSV 和诊断截图发回分析。**

## Tier 1：受控低速首轮

**场地要求**：封闭/空旷、**有车道线**（无标线的空停车场 AP 可能到不了
激活态，验证不到资格段）、低速（AP 最低激活速度之上即可，越低越好）。

**准备**：录制器开 120s，过滤 `45,399,3EE`（Tier 0 确认 0x488 可见则
`45,399,3EE,488`）；诊断页在手机上可见；开关确认 armed
（reason=waitApActive）。**AP 注入门控必须开**（驾驶舱页）——门控关=
机制不运行（Tier 1 会白跑）；「8.3.6防甩机制」开关也必须开。

**每轮动作**：正常激活 AP（拨杆或车机）。然后**只观察，不操作**：

1. AP 激活后约 0.2-0.5s → 设备合成取消 → AP 掉（0x399 → 状态 1）；
2. **静默等待约 1-1.5s**（设备等 0x399 回状态 2=可用，诊断
   reason=`waitAvailable`，此间设备零发送、AP 保持关闭）；
3. 车回可用态后 → 设备合成重请求 → AP 恢复（2→3 约 0.2s，资格窗口
   最长 2.4s）→ bit46 注入；
4. **观察这一次最终激活的方向盘体感**（这就是假设要回答的问题）；
5. **观察激活保持时长**：若激活后短时掉线（~250ms 后 6→1，无甩动无
   8/9），记录掉线时延——多轮数据才能区分"单帧断言不足"与其它原因。

**单 CAN 特有观察项（每轮都看）**：诊断格「**回声 / 冲突**」——
own-echo 计数应在设备每次合成 0x045 后稳步 +1（自己发的帧被正确识别为
回声而非车侧新输入）；**冲突计数必须为 0**。若首轮即出现
`counterConflict` 锁死 → **停测**，CSV 发回（单总线上 counter 锚定的
time-recency 规则在你的接线/收发器下可能需要重新标定——这是双 CAN
数据不继承的核心原因）。

双手不离方向盘。任何时候：物理拨杆或刹车=立即取消 AP（若正处于握手术
中则本轮同时锁死——正常，开关关→开再测）。

**每轮结束记录**：诊断里的 `reason` / 轮次计数器 / **上次结束原因** /
**自动重武装**计数（跨开关操作保留）/ **回声与冲突计数**（单 CAN 新增）/
下载或标注 CSV 时段。**仍建议先记 reason 再做任何开关操作**——
`lastEndedReason` 已跨重武装与状态变化保留，但截图留档永远最稳。
建议 3-5 轮起步（双 CAN 凑了 9 轮才定位到甩动形态；单 CAN 是新的
数据集）。

**出错后的恢复动作**：
- **车辆侧异常无需任何操作**：窗口过期 / AP 退出 / AP 自恢复 / 故障态
  （状态行带"·已自动重武装"后缀）设备已自动回到武装态——正常重新激活
  AP（完整退出后）即开下一轮，**不用碰任何开关**；
- **连续 3 次车辆侧异常**（状态行 `autoRearmLimit`·锁定）→ 把
  「8.3.6防甩机制」开关 关→开 重置预算；连续 3 次说明车辆持续不配合，
  重置前先把 CSV 发回分析；
- **硬件类锁死**（计数器冲突/发送失败/许可丢失/物理拨杆/超时等，状态行
  带"·锁定"后缀）→ 同样开关 关→开；**不需要动 AP 门控**；
- **不要用关门控来恢复**：门控关 + FSD 注入开 = 旧直通路径立即恢复
  bit46 自由注入（历史猛甩路径，见方案 A 的警告）；
- 记住锁死期间的语义：开关开 + 锁死 = 设备**暂停一切** FSD 激活注入
  （此时激活不会有反应，是设计行为不是设备坏了）——先看状态行的
  中文 reason，再决定重武装还是停测。

### 结果判读（Go / No-Go）

| 观察到的 reason / 现象 | 含义 | 动作 |
|---|---|---|
| `cancelEvidenceTimeout` | 车没接受我们的合成取消手势 | **停测**，CSV 发回分析 |
| `waitAvailable`（持续中） | 正常中间态：取消已生效，等车回状态 2 | 正常等待，无需操作（最长 3s） |
| `availableWaitTimeout` | 车接受了取消但 3s 内没回可用态 | 记录并重测一轮；连续出现则发回分析 |
| `apActiveDuringWait`（已自动重武装） | 取消生效后 AP 又自己恢复激活（无需重请求） | **无需操作**，正常开下一轮；若体感异常则停测发回 |
| `apFaultState`（已自动重武装；激活后 6→8→9→1 级联） | 司机干预/脱手检测触发车辆级联（双 CAN 曾见：激活 182ms 后级联，0x488 大幅摆动=有物理转向输入） | 激活瞬间轻扶方向盘别用力；无需开关，直接重测 |
| `apExitedDuringWindow`（已自动重武装；重请求后车回 state 1） | 车辆偶发拒绝重请求（编码/计数器/回显全对，车辆侧条件不满足） | 无需开关直接重测；连续出现则发回 CSV |
| `autoRearmLimit`（连续车辆侧异常·锁定） | 连续 3 次车辆侧异常，预算用尽真锁死 | 开关 关→开 重置（先发 CSV 分析车辆为何持续不配合） |
| `qualified`→Complete，激活不甩 | 假设的正面证据 | 继续凑轮次；仍属单车小样本 |
| 激活后短时掉线（~250ms 后 6→1，无甩动无 8/9） | 车自掉；疑单帧 bit46 断言不足（掉线在下一 1Hz 载波前） | 记录轮次+掉线时延，继续测；凑数据后鉴别 |
| `windowExpired`（已自动重武装） | 0x3EE 载波节奏抖动（窗口 2.4s，双 CAN 预期命中率≈100%） | 无需操作；频繁出现则发回分析 |
| `physicalInput` | 握手术中碰了拨杆 | 开关关→开，重测一轮 |
| 按杆后 AP 没反应 1-2 秒，「车辆响应」格显示**「未接受激活 · 车侧拒绝」**（P1） | **车侧拒激活**（双 CAN 162535 CSV 实锤过：flag1 翻起但永不 state3；设备正常，phase 保持 WaitDriverIntent） | **勿连按**——稍等 2-3 秒再按一次；连拒多次则录 CSV 发回，`apFlagCounts` 直方图可顺带对照 flag 语义 |
| 回声计数不涨 / 涨得异常（每轮合成 2 帧应 +2） | **单 CAN own-echo 识别异常**（接线/回环路径与双 CAN 不同） | **停测**，CSV 发回（这是本规程新增的硬判读项） |
| `apGateOff` / `effective=false` | AP 门控被关（机制静默，Legacy 走直通） | 重开门控即恢复武装，**无需**动 8.3.6 开关 |
| `counterConflict` / `txFailed` / `permitLost` | 底层发送/许可问题（counterConflict 在单 CAN 上是**首验项**，不是已知良性事件） | **停测**，发回诊断 |
| 激活仍甩 / 出现新异常体感 | 假设不成立或更糟 | **立即开关 off，停测**，发回 CSV |

测完开关关。任何"通过"都如实记录为**单车、当日、小样本**观察，
不表述为"方向盘猛甩已修复"。

## 方案 A：原生激活对照鉴别测试（甩幅归因）

**要回答的问题**：双 CAN 两份 CSV 已定位甩动时序=state6 后 186-330ms
固定相位的**车固有 FSD 初始车道捕捉**（最大 42.6° trackAngle 三拍摆动），
但**协调器的取消→重请求打断是否放大了这一捕捉**仍无法排除。本测试用
**旧直通路径的原生激活**（无打断、无取消重请求）作对照组。

**⚠️ 本测试故意重现历史猛甩路径**（关门控 + FSD 注入开 = bit46 从 CAN
活跃起常注，即 8.3.6 之前的旧路径）。只在封闭场地、低速、双手全程不离
方向盘时做；任何异常体感立即 FWD 取消。

**设置**（与 Tier 1 完全相反的一组开关）：

1. 「8.3.6防甩机制」开关**关**（门控关时它本就不运行，关掉更干净）；
2. 驾驶舱页「AP 注入门控」**关**——此时 Legacy 直通路径合法接管
   （框架的正常设计模式）；
3. FSD 注入总开关**开**（稳定模式）——bit46 直通注入；
4. 录制器开 120s，过滤 `45,399,3EE`（+`488` 若 Tier 0 确认可见）。

**每轮动作**：低速行驶中**原生 RWD 拨杆激活 FSD**（设备不干预——无
取消、无重请求、无打断，bit46 从 CAN 活跃起持续注入）。观察初始车道
捕捉体感。3-5 轮。随时 FWD 取消。

**对照组**：**必须用同一台单 CAN 设备在相近场地跑协调器组**
（上面 Tier 1 的 3-5 轮）。**双 CAN 的 9 轮不能作为单 CAN 的对照组**
——接线、收发器、回声路径全不同，甩幅分布没有可比性（它只用来定性
"车固有捕捉"这个形态是否存在）。

**分析方法**（CSV 发回后由 Claude 做）：若 0x488 可见，对每轮取
state→6 后 186-330ms 固定相位窗内 0x488 trackAngle（b0b1 大端 −16384，
×0.1°，仅 type=2 帧）的最大单拍 |Δangle| 与总摆幅，两组对比：

- 原生组摆幅 ≈ 协调器组（同量级分布）→ **打断不放大**，甩=车固有
  （初始车道捕捉），协调器无责，防甩假设不受损；
- 原生组明显更小（如全部 <5° 而协调器组屡现 >10°）→ **打断放大实锤**
  → 先设计后报批，不直接改代码。

**0x488 不可见时的降级**：鉴别退化为体感对照 + 0x399 时序对照（掉线
形态、8/9 级联有无），结论只能给到定性。

**做完立即恢复**：门控重新打开（8.3.6 防甩机制随之恢复武装）。注意
关门控期间是历史猛甩路径在跑——测试窗口之外不要保持此开关组合。
